## Phase 14 — CUDA / GEMM / cuBLAS investigation

**Goal:** explain what Phase 13 observed:

- prefill: 87% GPU utilization, `ampere_sgemm_*` kernels
- decode: 37% GPU utilization, `gemv` kernels

This phase only measures; nothing is optimized.

### What the script does

`profiles/phase14/gemm_benchmark.py` runs nine experiments and writes `results.json` plus a
generated `findings.md`:

| experiment | spec | what it measures |
|---|---|---|
| `trace` | 14.3 | the chain `nn.Linear` → `aten::linear` → `aten::t` + `aten::mm` → cuBLAS kernel |
| `model_tensors` | 14.9 | shape / stride / contiguity of the real tensors entering each Linear (forward hooks) |
| `layer_table` | 14.4–14.5 | M, K, N, FLOPs and arithmetic intensity of every matmul in the model |
| `roofline` | 14.6, 14.10 | measured peak FP32 / TF32, DRAM bandwidth, cost of one kernel launch |
| `m_sweep` | 14.11 | every Linear shape at M = 1…512: kernel chosen, µs, TFLOPS, GB/s, split-K |
| `tf32_sweep` | 14.10 | which kernels change when TF32 is allowed (Tensor Cores) |
| `batching` | 14.12 | B separate `[1,K]` calls vs one `[B,K]` call |
| `forward_estimate` | 14.5 | isolated matmul times summed over a forward, vs Phase 13 |
| `kv_cat` | 14.13 | cost of `torch.cat` KV growth vs sequence length |

### Key code

**FLOPs, bytes and arithmetic intensity (14.5).** Arithmetic intensity is what decides
compute-bound vs memory-bound.

```python
def gemm_cost(M: int, K: int, N: int, elem_bytes: int = BYTES_FP32) -> dict:
    flops = 2 * M * K * N
    bytes_moved = elem_bytes * (M * K + K * N + M * N)
    return {
        "M": M, "K": K, "N": N,
        "flops": flops,
        "bytes": bytes_moved,
        "weight_bytes": elem_bytes * K * N,
        "arithmetic_intensity": flops / bytes_moved,
    }
```

At M=1, every weight value is used exactly once, so the intensity is about 0.5 FLOP/byte. At
M=128 it is about 48 FLOP/byte. This GPU's ridge point is about 26 FLOP/byte: below it a
kernel is memory-bound, above it compute-bound.

**Tracing `nn.Linear` down to the backend (14.3).** A `TorchDispatchMode` records every ATen
op that reaches the CUDA backend, with its strides (condensed from `gemm_benchmark.py`):

```python
class AtenLogger(TorchDispatchMode):
    def __torch_dispatch__(self, func, types, args=(), kwargs=None):
        out = func(*args, **(kwargs or {}))
        self.calls.append({"overload": str(func),
                           "inputs": [describe(a) for a in args if isinstance(a, torch.Tensor)],
                           "output": describe(out) if isinstance(out, torch.Tensor) else None})
        return out
```

It showed that `aten::linear` is not a kernel. It becomes `t` (a free transpose *view*),
`view`, one `mm`, and `_unsafe_view`. Because cuBLAS is column-major, the transposed weight
view is passed with op `T`, which explains the `_tn` in `ampere_sgemm_128x64_tn`.

**Output tiles vs SMs (14.8).** Parsing the tile size out of the kernel name shows why split-K
appears: 22 output tiles are barely enough for 20 SMs.

```python
def output_tiles(kernel: str, M: int, N: int) -> int | None:
    match = TILE_RE.search(kernel)             # "_128x64_" in ampere_sgemm_128x64_tn
    if not match or "gemm" not in kernel:
        return None
    tile_n, tile_m = int(match.group(1)), int(match.group(2))
    return math.ceil(N / tile_n) * math.ceil(M / tile_m)   # cuBLAS sees C^T [N, M]
```

### Run

```bash
python profiles/phase14/gemm_benchmark.py          # ~10 s
python profiles/phase14/gemm_benchmark.py --quick
pytest tests/test_gemm_benchmark.py
```

### What it found

| | prefill (M=128) | decode (M=1) |
|---|---|---|
| gate/up kernel | `ampere_sgemm_128x64_tn` | `internal::gemvx::kernel` |
| intensity | ~48 FLOP/B (compute-bound) | 0.5 FLOP/B (memory-bound) |
| throughput | ~2.4 TFLOPS | ~0.05 TFLOPS at ~100 GB/s |

- Decode reads all 116 MB of weights for 61 MFLOP of work.
- In decode, each kernel launch costs more CPU time (~14 µs of wall time per launch) than
  the kernel runs on the GPU (~5 µs). So decode is **launch-bound**, not just memory-bound.
- Batching 32 one-token calls into one `[32,K]` call is ~21× faster.
- Growing the KV cache with `torch.cat` copies 2 GB to append 3 MB over a 384-token
  generation.
- **Pitfall:** the 4096² "peak FP32" GEMM measured *below* the model's own GEMMs, because of
  the laptop's clocks. The script takes the best observed point as the peak.

## Phase 15 — kernel-level optimization

**Goal:** make the engine faster **without changing outputs**, one change at a time. Each
change must pass a correctness gate, and it is kept only if it gives a measured speedup.

### 15.1 Preserve the baseline: opt-in fast paths

`src/model/fast_paths.py` holds process-global flags, all `False` by default. The model checks
them in place, so with every flag off the model runs the Phase 13 code path.

```python
@dataclass(frozen=True)
class FastPaths:
    rope_cache: bool = False
    fused_rmsnorm: bool = False
    decode_no_mask: bool = False
    sdpa_gqa: bool = False
    fused_qkv: bool = False
    fused_gate_up: bool = False
    last_token_logits: bool = False

@contextmanager
def enabled(**flags):
    """Temporarily run with exactly these flags on (others off)."""
    global FLAGS
    previous = FLAGS
    set_flags(**flags)
    try:
        yield FLAGS
    finally:
        FLAGS = previous
```

Usage:

```python
from src.model import fast_paths

fast_paths.prepare(model)          # builds fused q/k/v and gate/up weight buffers
with fast_paths.enabled(rope_cache=True, fused_rmsnorm=True, decode_no_mask=True):
    logits, _ = model(input_ids, kv_cache=cache)
```

`prepare()` concatenates the q/k/v weights into one buffer and turns the original `Linear`
weights into **views** of it (`fuse_linears`). Nothing is duplicated in memory, and the fused
and unfused paths always see the same values.

### 15.3–15.5 Preallocated KV cache (`StaticKVCache`)

This replaces "allocate T+1 rows and copy T old + 1 new, every step" with "write 1 row in
place". It has the same interface as `KVCache`, so the model, `ModelRunner` and
`BatchedKVCache` don't need to know which one they have (`src/inference/kv_cache.py`).

```python
def update(self, layer_idx, key, value):
    start = self.lengths[layer_idx]
    end = start + key.shape[2]

    if end > self.capacity:
        raise ValueError(f"StaticKVCache overflow: {end} tokens > capacity {self.capacity}")

    if self.key_cache[layer_idx] is None:
        self._allocate(layer_idx, key)        # [B, H, capacity, D], dtype/device from key

    with region("kv_cache/write"):
        self.key_cache[layer_idx][:, :, start:end].copy_(key)
        self.value_cache[layer_idx][:, :, start:end].copy_(value)

    self.lengths[layer_idx] = end

    return (                                  # views of the buffer: no copy
        self.key_cache[layer_idx][:, :, :end],
        self.value_cache[layer_idx][:, :, :end],
    )
```

It is selected through the runner, and the engine uses it too when `paged_kv=False`:

```python
runner = ModelRunner(model, tokenizer, sampler, kv_cache="static")   # default: "dynamic"

def new_kv_cache(self):
    num_layers = self.model.config.num_layers
    if self.kv_cache_kind == "static":
        return StaticKVCache(num_layers, capacity=self.max_seq_len)
    return KVCache(num_layers=num_layers)
```

### 15.6–15.7, 15.12 Launch reductions and avoiding unnecessary work

Each flag is one change at the place in the model where the work happens.

**`rope_cache`** (`src/model/rope.py`): the cos/sin tables are built once, already
interleaved. That removes 4 `repeat_interleave` kernels per layer. It is bit-exact.

```python
if fast_paths.FLAGS.rope_cache:
    if position_ids is not None:
        cos = self.cos_interleaved[position_ids].unsqueeze(1)
        sin = self.sin_interleaved[position_ids].unsqueeze(1)
    else:
        cos = self.cos_interleaved[start_pos:start_pos + seq_len]
        sin = self.sin_interleaved[start_pos:start_pos + seq_len]
    return x * cos + self.rotate_half(x) * sin
```

**`fused_rmsnorm`** (`src/model/rmsnorm.py`): one kernel instead of six.

```python
if fast_paths.FLAGS.fused_rmsnorm:
    return F.rms_norm(x, (x.shape[-1],), self.weight, self.eps)
```

**`decode_no_mask`** (`src/model/attention.py`): a single new query sees every cached key,
so the mask would be all-True. Skipping it also lets SDPA avoid its masked path.

```python
elif T == 1 and fast_paths.FLAGS.decode_no_mask:
    attn_mask = None
    is_causal = False
```

**`fused_qkv`**: one matmul, then split. `fused_gate_up` does the same thing in `swiglu.py`.

```python
if fast_paths.FLAGS.fused_qkv and self.qkv_weight is not None:
    kv_dim = self.num_kv_heads * self.head_dim
    q, k, v = F.linear(x, self.qkv_weight).split([self.hidden_dim, kv_dim, kv_dim], dim=-1)
```

**`sdpa_gqa`**: `enable_gqa=True` instead of materialising 4× K/V copies with
`repeat_interleave`.

**`last_token_logits`** (`src/model/model.py`): when nothing needs the other positions (no
targets, no padding mask), run the final norm and the LM head on the last position only.

### 15.15 The correctness gate

`src/inference/correctness.py` compares any variant (a runner + flags) against the baseline:

```python
reference = Variant("baseline", ModelRunner(model, tok, sampler))
candidate = Variant("fast", ModelRunner(model, tok, sampler, kv_cache="static"),
                    {"rope_cache": True, "fused_rmsnorm": True})
gate = run_gate(reference, candidate, prompts, tokenizer)
assert gate.passed, gate.failures()
```

| check | what it compares |
|---|---|
| `prefill_logits` | last-position logits after each prompt (max / mean abs error) |
| `decode_logits` | teacher-forced decode: both sides are fed the *reference's* tokens, so errors can't compound |
| `greedy_tokens` | free-running greedy generation, token for token |
| `eos` | EOS set to the token the reference emits at step 5: both must stop at the same step |
| `kv_cache` | cached decode vs a full no-cache recompute |
| `batched` / `batched_independent` | prompts of different lengths through the continuous-batching engine: equal to the reference, and each equal to its own single-request run |

Logits need max abs error ≤ 1e-3 and mean abs error ≤ 1e-4. Tokens must match exactly.

### 15.2 The optimization loop: paired timing and keep/reject

`profiles/phase15/phase15_benchmark.py` runs the ladder: for each candidate, apply one change,
gate it, benchmark it, profile it, then keep or reject it.

**Pitfall found here:** the first version timed each configuration on its own. The same
baseline measured **3.3 ms/token at the start and 4.7 ms at the end** of a run, because laptop
clocks drift and decode is CPU-bound. That made good changes look like regressions. The fix is
**paired, interleaved timing**: previous and candidate configs alternate A B B A … in the same
time window, and the decision uses the median per-round ratio.

```python
for i in range(rounds):
    for key in (("a", "b") if i % 2 == 0 else ("b", "a")):
        flags, pre, setup, dec = sides[key]
        with fast_paths.enabled(**flags):
            times[key]["prefill"].append(median(time_ms(pre, repeats=5, warmup=0)))
            times[key]["decode"].append(time_ms(dec, setup, repeats=1, warmup=0)[0] / steps)

ratios = [b / a for a, b in zip(times["a"][metric], times["b"][metric])]   # < 1: B faster
```

```python
def decide(pair, gate, threshold):
    if not gate.passed:
        return False, "rejected: correctness gate failed (...)"
    d_gain = 1 - pair["decode"]["ratio"]
    p_gain = 1 - pair["prefill"]["ratio"]
    if d_gain < -threshold or p_gain < -threshold:
        return False, "rejected: regression (...)"
    if d_gain >= threshold or p_gain >= threshold:
        return True, "kept: ..."
    return False, "rejected: within noise (...)"
```

The script also runs these side experiments:

- decode batching (B = 1…16)
- an attention study (15.11): mask vs no mask, `enable_gqa` vs `repeat_interleave`, SDPA
  backends, as the KV length grows
- a kernel-launch overhead experiment (15.14)
- a per-region kernel inventory (which ops launch the most kernels)
- a baseline re-run at the end, as a drift check

`src/inference/profiler.py` gained `profile_workload(..., regions=False)`. A compiled model
would otherwise recompile for the `record_function` calls.

```bash

python profiles/phase15/phase15_benchmark.py --quick
python profiles/phase15/phase15_benchmark.py --skip-compile

```

### What it found

| change | Δ decode (paired) | decision |
|---|---|---|
| `StaticKVCache` | −0.2% | within noise at a 128-token context (bit-exact, so harmless) |
| `rope_cache` | +10.0% | **kept** |
| `fused_rmsnorm` | +14.5% | **kept** |
| `decode_no_mask` | +17.7% | **kept** |
| `sdpa_gqa` | −24.9% | rejected (see below) |
| `fused_qkv` / `fused_gate_up` | +2.2% / +0.2% | within noise |
| `last_token_logits` | +7.6% prefill | **kept** |
| `torch.compile(dynamic=True)` | +26.6% | **kept** |

**Final configuration vs the baseline:**

- decode **2.05×** faster (3.92 → 1.91 ms/token)
- prefill 1.22× faster
- kernel launches per decode step: 424 → 132
- correctness gate passed (max |Δlogit| 3.05e-5)

**Lessons:**

- `sdpa_gqa` *lowered* GPU time but raised launches, and wall time went up. In fp32, SDPA's
  memory-efficient kernel can't take `enable_gqa`, so it falls back to the unfused math path:
  11 kernels instead of 3. Decode is launch-bound, so fewer launches matters more than less
  GPU work.
- `torch.compile` costs about 10 s up front for the first calls, so cold and steady-state
  numbers are reported separately.
- Engine defaults are unchanged. Every optimization is opt-in.

## Phase 16 — deep mapping against vLLM

**Goal:** freeze our engine, map every component onto vLLM's production engine using its real
source, and compare the two on the same workload.

### Studying the vLLM source

vLLM (commit `8b84e15`, V1 engine) was cloned outside the project. It was studied along the
spec's 16.16 path: entry point → engine → scheduler → KV cache → model runner → attention →
sampler. For every component the study answered: what problem it solves, what data it owns,
who calls it, what it calls, what state it keeps, and how it touches the GPU. Key citations
were checked against the source. The results are in `Docs/FINAL_ARCHITECTURE.md` §18.

### Making vLLM run *our* model: `export_llama.py`

V1 is already a Llama-family decoder (GQA, RoPE, RMSNorm, SwiGLU, tied embeddings, no
biases). The one difference is how RoPE pairs dimensions:

- ours rotates interleaved pairs `(2i, 2i+1)`
- Llama rotates halves `(i, i+32)`

Reordering each head's q/k projection rows converts one layout into the other. Because q and k
get the *same* permutation, q·k is unchanged, so the model computes the same function.

```python
def rope_permutation(head_dim: int) -> torch.Tensor:
    """Interleaved-pair order -> half-split order: [0, 2, ..., D-2, 1, 3, ..., D-1]."""
    return torch.cat([torch.arange(0, head_dim, 2), torch.arange(1, head_dim, 2)])


def permute_heads(weight: torch.Tensor, num_heads: int, head_dim: int) -> torch.Tensor:
    """Reorder the output rows of a [num_heads*head_dim, in] projection within each head."""
    perm = rope_permutation(head_dim)
    w = weight.view(num_heads, head_dim, -1)[:, perm, :]
    return w.reshape(num_heads * head_dim, -1).contiguous()
```

The script builds a `LlamaForCausalLM` with transformers and verifies it against our model. It
refuses to save if the result doesn't match. Measured: max |Δlogit| 1.7e-5, identical greedy
tokens. The output goes to `models/v1-llama`.

### Freeze and same-workload comparison: `engine_vs_vllm.py`

| job | what it writes |
|---|---|
| freeze (16.1) | `engine_freeze.json`: model config, checkpoint and tokenizer sha256, components and default settings, runtime (torch, CUDA, GPU, driver, SDPA backends), hash of every `src/` file, stored Phase 13–15 results |
| workload | `workload.json`: the same prompt token ids, `max_new_tokens`, EOS id and batch size for both engines |
| ours | `results_ours.json`: the baseline and the Phase 15 optimized engine through the Phase 12 harness (TTFT, ITL, tokens/s, peak memory, generated tokens) |
| vllm | `results_vllm.json`: vLLM stepped by hand so every token is timestamped the same way; token ids go in directly (`skip_tokenizer_init`) |
| report | `COMPARISON.md`: the tables, token equality, and the mechanisms that explain each difference |

vLLM pins its own PyTorch/CUDA build, so its half runs in a separate environment. The vLLM
code path imports nothing from this project.

```bash
python profiles/phase16/export_llama.py                     # once
python profiles/phase16/engine_vs_vllm.py                   # freeze + ours + report
# in a separate venv with vllm installed:
python profiles/phase16/engine_vs_vllm.py --engine vllm
python profiles/phase16/engine_vs_vllm.py --report
```

### What it found (our side)

| scenario | tokens/s, baseline → optimized | speedup |
|---|---|---|
| single request | 311 → 522 | 1.68× |
| 16 concurrent requests | 867 → 898 | 1.04× |

The Phase 15 changes target launch overhead, which is the single-request bottleneck. The
batched path is dominated by **KV data movement** instead:

- paged blocks are gathered back into contiguous K/V every step
- all rows' caches are padded and concatenated
- prompts are padded
- `torch.compile` graph-breaks at `position_ids.max().item()`

These are exactly the costs that vLLM's paged-attention kernel, flat unpadded token batch and
CUDA graphs remove. The vLLM row is pending until the vLLM side is run in its own environment.

**Pitfall:** the first workload gave every batch prompt the same length (32 tokens) because of
a modulo bug, `(i*97) % 97 == 0`. It was fixed to produce lengths from 32 to 125 tokens.
