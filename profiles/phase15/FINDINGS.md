## KV cache: did eliminating `torch.cat()` reduce copy/allocation overhead?

| decode, per step | baseline (`torch.cat`) | preallocated (`copy_` in place) |
|---|---|---|
| KV region calls | 8 `kv_cache/cat` | 8 `kv_cache/write` |
| KV region GPU ms | 0.043 | 0.021 |
| KV region CPU ms (profiled) | 0.287 | 0.296 |
| copy/cat kernels GPU ms | 0.185 | 0.167 |
| launches | 424 | 424 |
| decode ms/token (paired) | 4.538 | 4.566 |
| peak MB (generation) | 142.5 | 148.4 |

Decision: **rejected: within noise (±3%; decode -0.2%, prefill -1.5%)**. The in-place write still launches one copy kernel per K and per V per layer, the same count as `cat`, but each kernel now copies 1 token instead of T+1, and nothing is allocated. At a 128-token context each `cat` moves only ~130 KB, so the saving per step is small in absolute terms. It grows linearly with context: Phase 14 counted 1.88 GB of copies for a full 512-token generation. The preallocated buffer costs 4 MB per sequence up front (capacity 512), versus `cat`'s transient old+new copies.

- **RoPE** (128 launches, 8 per q-or-k call): slice, 2x `repeat_interleave` (`copy_`), `mul`, `neg` + `stack` (`cat`) for `rotate_half`, `mul`, `add`. `rope_cache` removes the `repeat_interleave`s (→ 96); the rest needs a fused kernel (torch.compile does it).
- **RMSNorm** (102 = 6 x 17 norms): pow, mean, add, rsqrt, mul, mul. `F.rms_norm` makes it one kernel per norm (→ 17).
- **Mask + masked SDPA** (24 + 48): the decode mask costs 3 kernels per layer (2x `arange`, compare), and a masked memory-efficient SDPA call adds `fill_` kernels on top of the attention kernel. Unmasked decode: 0 + 8.
- **Matmuls**: each Linear is its own launch, 24 for q/k/v alone. `fused_qkv` makes that 1 per layer (8 per step), but it was not kept in this run (rejected: within noise (±3%; decode +2.2%, prefill +1.5%)): the matmuls at M=1 are GEMVs streaming the same weight bytes either way, so fusing saves only 2 launches per layer.
- **KV cache**: `torch.cat` (16 launches) would become an in-place `copy_` with the same launch count. The preallocated cache was not kept at this context length (see the KV section), so the final config still uses `cat`.

Prefill (T=128, causal), fp32 backend availability:

- **flash**: not available — No available kernel. Aborting execution.
- **efficient**: 32.6 us, `fmha_cutlassF_f32_aligned_64x64_rf_sm80`
- **math**: 82.3 us, `ampere_sgemm_128x128_nn`, `ampere_sgemm_128x128_tn`, `elementwise_kernel[CUDAFunctor_add]`, `vectorized_elementwise_kernel[AUnaryFunctor]`, `elementwise_kernel`, `(anonymous namespace)::softmax_warp_forw`, `reduce_kernel`, `vectorized_elementwise_kernel[FillFunctor]`, `triu_tril_kernel`, `vectorized_elementwise_kernel`, `vectorized_elementwise_kernel[FillFunctor]`
- default choice: `fmha_cutlassF_f32_aligned_64x64_rf_sm80`

- PyTorch already runs a **fused** SDPA kernel: one `fmha_cutlassF` (memory-efficient attention) launch computes QKᵀ, softmax and ×V together. The unfused reference needs several kernels. FlashAttention does not support fp32, so the memory-efficient kernel is the best fused option for this model's dtype.
- The decode mask is unnecessary: a single query at the last position sees every key. Building it costs 3 extra kernels per layer (2x `arange`, compare), and a masked call has to read the mask too.
- `repeat_interleave` for GQA materialises 4x copies of K and V every layer and every step. `enable_gqa=True` avoids them, but in fp32 the memory-efficient kernel does not accept it, so SDPA **falls back to the MATH backend**: identical kernels to the forced-math column, 11 launches instead of 3.
- That is why the `sdpa_gqa` rung was rejected even though it **lowered** GPU busy time per token (1.735 → 1.587 ms): it raised launches per step (245 → 309) and decode is launch-bound, so wall time went +25%. Less GPU work is not a win if it costs more launches.
- With a single query, the fused fp32 `fmha_cutlassF` kernel is not the fastest on the GPU: at T=16 the unfused QKᵀ/softmax/×V path takes 15.9 us of GPU time vs 26.1 us. The fused kernel is tiled for many queries (64-row blocks), and decode fills one row. It still wins on launches (fewer kernels), which is what matters at this model size.
- As T grows, decode attention time grows with the K/V bytes read, but it stays small next to the matmuls at this model's context of 512 or less.

Categories come from kernel names. Inductor's Triton kernels are named after the ops they fuse (e.g. `triton_poi_fused__scaled_dot_product_efficient_attention_..._mul`), so under torch_compile the fused elementwise work shows up as attention/other, not as elementwise.

None of the decode kernels are limited by arithmetic. Arithmetic intensity is about 0.5 FLOP/byte for the GEMVs (Phase 14) and lower still for elementwise ops (1 FLOP per 8 bytes read and written), so they are bound by DRAM bandwidth, or at this size by launch latency:
- **copy/cat** (`torch.cat` KV growth, `repeat_interleave`, `contiguous`, `rotate_half`'s `stack`) is pure data movement with zero arithmetic.
- **elementwise** (RoPE, RMSNorm, SiLU·mul, residual adds) reads and writes the whole activation for 1-2 FLOPs per element.
- **gemv** streams all 116 MB of weights once per token. It is the one data-movement cost that no fusion removes, only batching (reuse across rows) or fewer bytes per weight (lower precision).

## Kernel launch overhead (15.14)

Same total work (2^20 fp32 elements +1) split over N kernels, and N kernels on 1-element tensors:

| N kernels | elements each | wall us (same work) | GPU us (same work) | wall us (tiny) | GPU us (tiny) | wall us per tiny launch |
|---|---|---|---|---|---|---|
| 1 | 1,048,576 | 69.7 | 69.1 | 4.2 | 1.2 | 4.17 |
| 10 | 104,857 | 76.8 | 72.4 | 40.9 | 10.9 | 4.09 |
| 100 | 10,485 | 409.0 | 189.9 | 409.0 | 108.3 | 4.09 |
| 1000 | 1,048 | 4149.7 | 1385.4 | 4113.4 | 1083.2 | 4.11 |

The same work costs 60x more wall time when split into 1000 launches. GPU time grows too (69 → 1385 us), because every kernel has a floor of ~1.1 us, but the CPU cost is worse: ~4.1 us per launch no matter how little it computes. More GPU operations does not mean more useful computation. A decode step issued 424 launches in the baseline.

## Overall: which optimization actually produced a measurable improvement?

- **kv_preallocated** — rejected: within noise (±3%; decode -0.2%, prefill -1.5%)
- **rope_cache** — kept: decode +10.0%, prefill +2.4%
- **fused_rmsnorm** — kept: decode +14.5%, prefill +6.8%
- **decode_no_mask** — kept: decode +17.7%, prefill +0.5%
- **sdpa_gqa** — rejected: regression (decode -24.9%, prefill -12.9%)
- **fused_qkv** — rejected: within noise (±3%; decode +2.2%, prefill +1.5%)
- **fused_gate_up** — rejected: within noise (±3%; decode +0.2%, prefill +1.1%)
- **last_token_logits** — kept: decode -0.7%, prefill +7.6%
- **torch_compile** — kept: decode +26.6%, prefill +4.3%

Borderline (every |Δ| < 6%, twice the threshold): `kv_preallocated`, `fused_qkv`, `fused_gate_up`. Their true effect at this context is about the size of the run-to-run noise, so their keep/reject can flip between runs. They do no harm (the gate passes), they just don't pay for themselves here.

The measured decision, not the theory, sets the final configuration. A change marked "within noise" may still be worth having (e.g. the KV cache's copy cost only grows with context), but it did not make this workload measurably faster. All engine defaults are unchanged. Opt in with `ModelRunner(kv_cache="static")`, `fast_paths.prepare(model)` + `fast_paths.set_flags(...)` and/or `torch.compile`.
