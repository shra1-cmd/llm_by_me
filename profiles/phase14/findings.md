# Phase 14 — CUDA / GEMM / cuBLAS findings

Generated by `profiles/phase14/gemm_benchmark.py` on **NVIDIA GeForce RTX 3050 6GB Laptop GPU** (compute capability 8.6, 20 SMs, PyTorch 2.13.0+cu130, CUDA 13.0). fp32 matmul precision: `highest`. All numbers come from `results.json`; rerun the script to refresh both files.

Measured roofline of this GPU:

| peak FP32 GEMM (CUDA cores) | peak TF32 GEMM (Tensor Cores) | DRAM bandwidth | FP32 ridge point | CPU cost of one tiny kernel |
|---|---|---|---|---|
| 2.86 TFLOPS | 5.97 TFLOPS | 111 GB/s | 25.8 FLOP/byte | 4.6 us |

FP32 peak source: M sweep, [256,512]x[512,1408] (`ampere_sgemm_128x64_tn`). The "tiny kernel" cost is the CPU wall time per `x.add_(1)` on a 1-element tensor: Python + PyTorch dispatcher + `cudaLaunchKernel`, with ~no GPU work.

A kernel whose arithmetic intensity (FLOP per byte of DRAM traffic) is below the ridge point cannot be compute-bound: DRAM delivers bytes slower than the SMs consume them.

One forward: prefill does **7.80 GFLOP** of matmul work, decode **60.95 MFLOP** — 128x less — yet both read the same 116.24 MB of weights. The LM head is the largest single matmul (26% of prefill matmul FLOPs), and its weight is the embedding table itself.

Note: the model has **separate** q/k/v projections (512→512, 512→128, 512→128 because of GQA with 2 KV heads), not one fused `[512, 1536]` QKV matmul, and separate gate/up projections — so each forward launches 7 Linear matmuls per layer + the LM head = 57 matmuls (Phase 13 counted exactly 57 `aten::mm`).

## 1. What happens to `nn.Linear`?

Traced `nn.Linear(512, 1408, bias=False)` on an input of shape [1, 128, 512] (the prefill shape):

```text
nn.Linear.forward(x)
  -> F.linear(x, weight)                  # y = x @ weight.T (+ bias)
  -> aten::linear                          # CompositeImplicit op: decomposes
    -> aten::t [[1408, 512]]
      -> aten::transpose [[1408, 512]]
        -> aten::as_strided [[1408, 512]]
    -> aten::matmul [[1, 128, 512], [512, 1408]]
      -> aten::reshape [[1, 128, 512]]
        -> aten::view [[1, 128, 512]]
      -> aten::mm [[128, 512], [512, 1408]]   => GPU: Memset (Device), ampere_sgemm_128x64_tn
      -> aten::_unsafe_view [[128, 1408]]
```

What reaches the CUDA backend (`TorchDispatchMode`, below autograd):

| aten op | inputs (shape / stride) | output (shape / stride) |
|---|---|---|
| `aten.t.default` | [1408, 512] / [512, 1] | [512, 1408] / [1, 512] |
| `aten.view.default` | [1, 128, 512] / [65536, 512, 1] | [128, 512] / [512, 1] |
| `aten.mm.default` | [128, 512] / [512, 1]; [512, 1408] / [1, 512] | [128, 1408] / [1408, 1] |
| `aten._unsafe_view.default` | [128, 1408] / [1408, 1] | [1, 128, 1408] / [180224, 1408, 1] |

- `aten::linear` is not a kernel. With no bias and a 3-D input it becomes `t` (a free transpose *view*: weight [1408, 512] strides [512, 1] -> [512, 1408] strides [1, 512], no copy, not contiguous), `matmul` folds `[1, 128, K]` into `[128, K]` (`view`, free), then **one `aten::mm`**, then `_unsafe_view` back to 3-D. (With a bias it would be `aten::addmm` instead.)
- `aten::mm` on CUDA calls `at::cuda::blas::gemm`, i.e. `cublasGemmEx` / `cublasLtMatmul`. cuBLAS is column-major, so PyTorch asks for C^T = W · x^T: the weight's transposed view is passed as-is with op `T`, the activations with op `N` — that is the `_tn` suffix in the kernel name. No data is moved to make this work.
- The LM head is written as `x @ token_embedding.weight.T`, so it enters at `aten::matmul` directly but ends in the same `aten::mm`.

## 2. Why is prefill GEMM-heavy?

With 128 tokens every Linear is a real matrix-matrix product. For gate/up (`[128,512]x[512,1408]`): 184.55 MFLOP, minimum traffic 3.69 MB, arithmetic intensity **48 FLOP/byte** — above the ridge point (26), so the math, not DRAM, is the limit. Each weight value loaded into shared memory is reused for many tokens (every row of the tile).

Measured in isolation it runs `ampere_sgemm_128x64_tn` in 76.2 us of GPU time = **2.42 TFLOPS** (85% of this GPU's measured FP32 peak). Over a whole forward the isolated matmul kernels add up to 3.83 ms vs 4.52 ms of matmul kernels measured in the full model in Phase 13 (72.5% of prefill GPU time). GEMMs dominate prefill simply because they are where the FLOPs are: RMSNorm/RoPE/SiLU are O(T·d), matmuls O(T·d²).

## 3. Why is decode GEMV-heavy?

With one new token, M = 1: `[1,512]x[512,1408]` is a matrix-**vector** product. cuBLAS recognises this and does not launch a tiled GEMM at all — it launches `internal::gemvx::kernel`. Its arithmetic intensity is **0.50 FLOP/byte**: every weight is read from DRAM once and used for exactly one multiply-add. Nothing can be reused, so the kernel is a pure weight-streaming loop.

For 2 <= M <= ~16 cuBLAS uses `gemmSN_TN_kernel` — a *small-N* GEMM (cuBLAS sees C^T[N,M], so its "N" is our M): still essentially one pass over the weights, with each weight reused for the few rows. Only from M ~ 16-32 does it switch to tiled `ampere_sgemm_*` kernels that stage tiles through shared memory.

The LM-head gemv (`[1,512]x[512,15485]`, 30.24 MB of weights) runs at 114 GB/s (278 us). Small gemvs (q/k/v/out) are too short to reach full bandwidth at all: they are over before the memory pipeline fills, and the weights may even sit in the 1 MB L2.

## 4. Why is decode GPU utilization lower?

Phase 13 measured GPU utilization 87.4% for prefill vs 36.7% for decode, with a similar kernel count per forward (403 vs 424).

In the isolated loops below the only work is one Linear, so wall time per call = max(CPU cost to issue it, GPU time to run it):

| shape | M | wall us/call | GPU kernel us | GPU busy |
|---|---|---|---|---|
| q_proj | 1 | 9.8 | 10.1 | 100% |
| q_proj | 128 | 53.2 | 52.1 | 98% |
| k_proj/v_proj | 1 | 9.1 | 4.2 | 46% |
| k_proj/v_proj | 128 | 13.2 | 12.4 | 94% |
| out_proj | 1 | 14.4 | 4.2 | 29% |
| out_proj | 128 | 53.4 | 51.9 | 97% |
| gate_proj/up_proj | 1 | 28.5 | 27.7 | 97% |
| gate_proj/up_proj | 128 | 72.6 | 76.2 | 100% |
| down_proj | 1 | 30.0 | 29.4 | 98% |
| down_proj | 128 | 82.7 | 79.5 | 96% |
| lm_head | 1 | 278.9 | 278.2 | 100% |
| lm_head | 128 | 924.2 | 943.2 | 100% |

1. **Launch/dispatch bound.** Issuing one kernel costs the CPU ~4.6 us. In decode, 24 of the 57 matmuls per forward (k_proj/v_proj, out_proj) run for *less* GPU time than that, and so do almost all of the other kernels (RMSNorm, RoPE, SiLU, residual adds, cats: 1-5 us each). The GPU finishes each one and then waits for the next launch. In prefill the same kernels are fed 128 rows, the GEMMs run for tens to hundreds of us, and launches are hidden behind GPU work.

   Check against Phase 13 (whole forward, per kernel launch):

   | step | launches | wall us / launch | GPU us / kernel | GPU util |
   |---|---|---|---|---|
   | prefill | 403 | 17.7 | 15.5 | 87.4% |
   | decode | 424 | 13.8 | 5.0 | 36.7% |

   In decode the average kernel runs ~5 us but each launch takes ~14 us of wall time — the CPU cost of one PyTorch op (here: 4.6 us for a bare `add_`, 9.1 us for an `F.linear` whose kernel is only 4.2 us; model ops also pay `nn.Module` / Python overhead). The GPU work per launch is smaller than the CPU cost per launch, so the GPU idles. In prefill the kernels are ~3x longer and cover the launch cost, so the CPU runs ahead and the GPU stays fed.

2. **Too little parallel work per kernel.** At M = 128 a gate/up GEMM does 128x more math than at M = 1 for the same weight bytes, and runs at 2.42 TFLOPS. At M = 1 there is only enough work to saturate DRAM, not the SMs: 52 GFLOPS, 1.8% of peak. Even a "busy" decode GPU is mostly waiting on memory.

So low decode utilization is mostly the GPU **waiting for the CPU**, and when it does run, it runs memory-bound kernels. Faster GEMM math would fix neither; fewer launches (fusion, CUDA graphs) and more rows per launch (batching) would.

Caveat: the isolated loops call the same weights back-to-back, so shapes whose weights fit in the 1 MB L2 (q/k/v/out: <= 1 MB) can look faster than DRAM allows; in the model the other layers' weights evict them between calls.

Non-monotonic points — a *larger* M running faster — show that the kernel choice comes from a heuristic, not from timing every candidate: q_proj M=1 10.1 us > M=2 4.8 us; gate_proj/up_proj M=16 55.9 us > M=32 40.0 us; down_proj M=32 88.2 us > M=64 57.1 us; lm_head M=8 532.1 us > M=16 356.0 us.

Continuous batching (Phase 11) turns B requests' `[1,K]` rows into one `[B,K]` operand: one launch instead of B, one pass over the weights instead of B, and arithmetic intensity grows ~linearly with B until the kernel becomes compute-bound. This is why decode throughput scales with batch size almost for free until M reaches the tens.

## 6. What is cuBLAS / cuBLASLt doing?

- **cuBLAS** is NVIDIA's BLAS: the classic `cublasSgemm` / `cublasGemmEx` API with heuristics that pick one of many precompiled kernels.
- **cuBLASLt** ("lightweight") is the newer matmul-only API (`cublasLtMatmul`) with explicit matrix layouts, epilogues (bias, activation fusion), workspaces and algorithm search. It exposes the split-K algorithms, whose reduction kernel carries the `cublasLt::` namespace. PyTorch uses cuBLASLt for many fp32/fp16 matmuls (and always for `addmm` with bias epilogues) and cuBLAS otherwise; both share the same kernel library underneath.
- Per call, the library looks at (M, N, K), dtype, transposes/strides (`tn`), alignment, the math mode (FP32 vs TF32 allowed), available workspace and the GPU architecture (sm_86 here), and picks an algorithm: GEMV for M=1, a tile size, whether to split K. That is why one `aten::mm` produced these different kernels across the sweep:

  - `ampere_sgemm_128x32_tn`
  - `ampere_sgemm_128x64_tn`
  - `ampere_sgemm_32x128_tn`
  - `ampere_sgemm_32x32_sliced1x4_tn`
  - `ampere_sgemm_64x32_sliced1x4_tn`
  - `cublasLt::splitKreduce_kernel`
  - `gemmSN_TN_kernel`
  - `gemv2T_kernel_val`
  - `internal::gemvx::kernel`

## 7. What does `ampere_sgemm_128x64_tn` mean?

| part | meaning |
|---|---|
| `ampere` | kernel written for the Ampere architecture (sm_80 family); the RTX 3050 is sm_86 and runs it |
| `sgemm` | **S**ingle-precision (FP32) GEMM, executed with FFMA instructions on the CUDA cores — not Tensor Cores (those kernels are named `*_tf32_*`, `*_s1688gemm_*`, `*_16816gemm_*`, `cutlass_*_tensorop_*`) |
| `128x64` | each thread block (CTA) computes a 128 x 64 tile of the output. Because cuBLAS works on C^T, the 128 runs along N (output features) and the 64 along M (tokens) |
| `tn` | operand ops: first operand (our weight view) **T**ransposed, second (activations) **N**ot transposed — the natural result of `x @ W.T` on row-major tensors |

For gate/up at M=128 that is ceil(1408/128) x ceil(128/64) = 22 CTAs for 20 SMs — barely one block per SM, far fewer than the GPU can hold at once, so per-SM latency hiding is poor. That is the situation where cuBLAS reaches for smaller tiles or split-K (section 8). Variants like `ampere_sgemm_32x32_sliced1x4_tn` use a smaller tile (more CTAs for small matrices) and split K across the 4 warps inside a block (`sliced1x4`).

## 8. What is `cublasLt::splitKreduce_kernel` doing?

Split-K: when the output has too few tiles to fill the GPU but K is long, the library splits the K (reduction) dimension into S slices. S x more CTAs each compute a partial `[tile]` product over K/S, write it to a workspace, and a second small kernel — `splitKreduce_kernel` — sums the S partials (and applies alpha/beta) into C.

```text
C[M,N] = A[M, K0:K1] B[K0:K1, N] + A[M, K1:K2] B[K1:K2, N] + ...
         └── CTA group 1 ──┘      └── CTA group 2 ──┘
                    └──── splitKreduce_kernel ────┘
```

Cost: an extra launch and an extra pass over the partials in DRAM; benefit: enough CTAs to occupy every SM. In this run split-K was chosen for: q_proj M=32, q_proj M=64, q_proj M=128, k_proj/v_proj M=32, k_proj/v_proj M=64, k_proj/v_proj M=128, k_proj/v_proj M=256, out_proj M=32, out_proj M=64, out_proj M=128, down_proj M=16, down_proj M=32, down_proj M=64, down_proj M=128. Phase 13 saw it on 40 of the 57 prefill matmuls.

How much of the matmul time the reduction itself takes (M=128):

| shape | GEMM kernel | total us | splitKreduce us | share |
|---|---|---|---|---|
| q_proj | `ampere_sgemm_128x64_tn` | 52.1 | 17.4 | 33% |
| k_proj/v_proj | `ampere_sgemm_32x32_sliced1x4_tn` | 12.4 | 1.6 | 13% |
| out_proj | `ampere_sgemm_128x64_tn` | 51.9 | 17.5 | 34% |
| down_proj | `ampere_sgemm_128x64_tn` | 79.5 | 17.8 | 22% |

Some GEMMs instead launch a `Memset (Device)` right before the sgemm and no reduce kernel (q_proj M=256, q_proj M=512, k_proj/v_proj M=512, out_proj M=256, out_proj M=512, gate_proj/up_proj M=32, ...). This is most likely cuBLASLt clearing its workspace / output for a split-K variant that accumulates partials in place; the profiler alone cannot confirm which algorithm was chosen (that would need `CUBLASLT_LOG_LEVEL`).

## 9. What role do Tensor Cores / CUDA cores play?

- **CUDA cores** execute scalar FP32 FFMA. All fp32 kernels above (`*sgemm*`, `gemv*`) run here. This is what the model uses today because PyTorch's default `float32_matmul_precision` is `"highest"` (TF32 off).
- **Tensor Cores** execute small matrix-multiply-accumulate tiles per instruction. On Ampere they accept FP16/BF16/INT8 and **TF32** (FP32 range, 10-bit mantissa) inputs, accumulating in FP32.
- Measured peak on this GPU: FP32 2.86 TFLOPS (`ampere_sgemm_128x64_tn`) vs TF32 5.97 TFLOPS (`cutlass_80_tensorop_s1688gemm_128x256_16x3_tn_align4`).

Tensor Cores only raise the compute ceiling. They help prefill GEMMs (compute-bound) and do nothing for M=1 gemvs, which are bound by reading FP32 weights — there the lever is fewer bytes (FP16/BF16/INT8 weights), not faster math.

All activations entering Linears are contiguous row-major fp32 and all weights are contiguous `[N, K]`; the only transpose is the free `W.t()` view that cuBLAS consumes as op `T`. No hidden `.contiguous()` copies happen before any matmul.

**The KV-cache `torch.cat` problem.** `KVCache.update` does `torch.cat([old, new], dim=2)` for K and V in every layer at every step: allocate a `[1, 2, T+1, 64]` tensor, copy T old rows, copy 1 new row.

- Per decode step: 16 `cat` calls, 16 new CUDA allocations (caching allocator, so no `cudaMalloc`, but a fresh block each time), 0.197 ms of stream time with a 128-token prompt.
- Generating 384 tokens after a 128-token prompt copies **1.88 GB** to append only 3.00 MB of new K/V (641x) — quadratic in sequence length. The whole cache at the end is only 4.00 MB.
- At this model size each cat is so small that its cost is the launch, not the copy; the quadratic byte growth would dominate for long contexts and bigger models. Phase 15 question: preallocate and write in place.

**Summary**

- Prefill: 7.80 GFLOP of matmul per forward, compute-bound FP32 SGEMMs on CUDA cores at 2.04 TFLOPS; the GPU is busy.
- Decode: 60.95 MFLOP per token; the 116.24 MB of weights must be streamed from DRAM every step (~1.10 ms at full bandwidth, 1.14 ms measured in isolated gemvs); and ~57 matmul launches plus ~370 small elementwise/copy launches cost more CPU time than the GPU spends computing.
- Levers for Phase 15, in order of expected payoff for decode: fewer launches (CUDA graphs / fusion / torch.compile), bigger M (batching), fewer weight bytes (lower precision), in-place KV cache. Faster GEMM math (TF32) mainly helps prefill.
