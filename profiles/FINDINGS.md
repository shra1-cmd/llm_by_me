# Phase 13 — PyTorch execution profiling findings

Generated by `scripts/profile_inference.py` on **NVIDIA GeForce RTX 3050 6GB Laptop GPU**, checkpoint `checkpoints/v1/step_9950.pt`. All numbers come from this run; rerun the script to refresh them.

Wall time is measured without the profiler and with regions off; GPU times are summed kernel durations from the profiled run. `GPU utilization` = GPU busy / wall.

## Findings

### 1. Prefill and decode are different workloads

- **Prefill (128 tokens)**: 7.13 ms wall, GPU busy 6.23 ms (**87%** utilization). Kernels: gemm 72%, elementwise 14%, attention 7%, copy/cat 5%, reduction 2%, index/gather 0%.
- **Decode (1 token, 128-token cache)**: 5.84 ms/step wall, GPU busy 2.140 ms/step (**37%**). Kernels: gemv 58%, attention 15%, elementwise 15%, copy/cat 9%, reduction 2%, index/gather 1%.
- Prefill processes 128x more tokens but costs only 1.2x the wall time of one decode step: per token, prefill is 105x cheaper.
- Both launch about the same number of kernels per forward (403 vs 424); decode's kernels are just tiny. In decode every Linear has M=1 row, so cuBLAS picks **gemv** (matrix-vector) kernels instead of gemm.

### 2. CPU vs GPU time: decode is launch/dispatch-bound

- Per decode step the GPU works 2.140 ms out of 5.838 ms; the rest of the time it waits for the CPU to issue ~424 kernel launches through Python and the PyTorch dispatcher.
- Under the profiler the CPU spends ~13.68 ms/step inside the model's regions (inflated by profiler overhead) — far more than the GPU time.
- Implication for Phase 14/15: faster GEMM kernels alone would barely move decode latency for this model; fewer launches (fusion, CUDA graphs, torch.compile) would.
